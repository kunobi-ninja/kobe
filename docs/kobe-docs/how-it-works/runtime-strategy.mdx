# Runtime strategy

kobe's value is the fleet layer — pools, leases, admission, GitOps, golden
images, observability — kept uniform across runtimes. The runtimes themselves
are pluggable. Pick from what ships today.

## What to use

| Need | Backend | Status |
|---|---|---|
| Nested real clusters | `k3s` / `k0s` | Production default |
| High density, low overhead | `vcluster` | Production |
| Provider-managed real infra | `capi` | Available (no CI provider in-tree) |
| Full isolation, native fidelity | `pkobe` | Not available yet |
| Proxy-based virtual clusters | `vkobe` (kobe-sync) | On hold |

Configuration for each backend: [Backends](/docs/pools/backends).

## Density: vcluster

For high-density ephemeral clusters (CI), use **[vcluster](https://www.vcluster.com/)**
as `spec.backend.type: vcluster`. The operator deploys one instance per
`ClusterInstance` via the upstream Helm chart into a dedicated per-instance
namespace.

This backend inherits vcluster's syncer semantics and fidelity boundaries
(cloud identity such as IRSA, syncer coverage, version skew). Tenants who need
full cluster semantics should use k3s, k0s, or CAPI instead.

## Isolation: k3s / k0s / CAPI

Nested k3s and k0s are today's production path for real control planes and
nodes. CAPI delegates to an infrastructure provider you already run.

A native isolation runtime (pkobe) is tracked as
[#23](https://github.com/kunobi-ninja/kobe/issues/23) / [#24](https://github.com/kunobi-ninja/kobe/issues/24).
It is not a backend you can set on a pool.

## On hold: kobe-sync / vkobe

Development of the in-house proxy-based syncer — `kobe-sync` and the `vkobe`
backend — is paused. Maintaining translation fidelity for the Kubernetes
resource surface is a product of its own.

The code remains in the tree and existing vkobe pools keep working. Prefer
`vcluster` for new density pools. Do not start a new vkobe pool.
