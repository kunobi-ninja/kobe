# Architecture

kobe is an in-cluster operator with an embedded HTTP API. Callers never talk to Kubernetes as themselves. They authenticate to the API; the operator creates lease objects and binds them to warm capacity.

## Components

| Piece | What it does |
|---|---|
| `kobe-operator` | Controllers plus the HTTP API. Multi-replica with leader election: only the leader runs controllers; every replica serves the API. |
| Pool manager | In-process. Decides create / bind / recycle / destroy for each pool. |
| Backends | Provision a `ClusterInstance` (k3s, k0s, vcluster, CAPI, vkobe). |
| Agent Sandbox | Upstream runtime for `SandboxPool` when `agentSandbox.mode` is `managed` or `external`. |
| `kobe` CLI | Client. Cluster leases get a kubeconfig; sandboxes get exec / logs / attach / SSH. |

## Cluster lease flow

```
parse request
    ↓
authenticate (SSH / OIDC / token)
    ↓
enforce AccessPolicy (pool allowlist, TTL cap, concurrency)
    ↓
create ClusterLease
    ↓
bind a Ready ClusterInstance
    ↓
return kubeconfig with a short-lived client certificate
```

The pool controller keeps enough `ClusterInstance` objects to satisfy `size` or `scaling.minReady`. The instance controller provisions and health-checks the backend. The lease controller binds, issues kubeconfig, and enforces release and expiry.

```
Creating → Ready (warm) → Leased → Recycling → destroyed, replaced
```

## Sandbox lease flow

```
parse request
    ↓
authenticate and enforce AccessPolicy.sandbox
    ↓
create SandboxLease
    ↓
admit against pool quota (ledger)
    ↓
bind a certified warm Sandbox (or create one)
    ↓
Ready — exec / logs / attach / port-forward
```

Callers never send a Pod spec. The `SandboxPool` template is the whole workload surface. See [Sandbox pools](/docs/pools/sandbox-pools).

`POST /v1/leases` admits either kind from the pool name. Clients do not pick Cluster vs Sandbox URLs. Kind-specific verbs (`exec`, `logs`, `attach`, `port-forward`, `executions`) are also served under `/v1/leases/:id/…`.

## Backends

The instance controller delegates provisioning to the pool's `spec.backend.type`. All backends satisfy the same contract — provision, health-check, readiness, recycle — so admission and leases behave the same. See [Backends](/docs/pools/backends) and [Runtime strategy](/docs/how-it-works/runtime-strategy).

Development of the in-house `kobe-sync` sidecar and the `vkobe` backend is on hold. Existing vkobe pools keep working; prefer `vcluster` for new density pools.

## API bounds

Concurrency is bounded at 200 simultaneous API requests. Infrastructure routes (`/healthz`, `/metrics`) are exempt.

| Binary | Role |
|---|---|
| `kobe-operator` | Operator + HTTP API |
| `kobe` | CLI |
| `crdgen` | CRD schema generator (build-time) |
| `kobe-sync` | Per-cluster runtime for `vkobe` (on hold) |
| `kobe-host-reaper` | Node DaemonSet; unmounts stale lease directories |
| `kobe-runner` | In-sandbox supervisor for durable exec and sessions |
